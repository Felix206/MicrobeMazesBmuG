Bacterial Simulation Tool

A Swing application that walks stochastic and deterministic bacterium models through pixel-grid mazes, then turns their trajectories into density maps and region-adjacency graphs. This page documents every class in the SURE package tree; what it owns, what it talks to, and which paths are live versus legacy. It also discusses batch processing/threading, a useful feature for large projects and data mining!

In total, there are 44 classes, 5 sub-packages, 7 categories, and 9 movement models

01

Core Simulation Engine

The physics, state, and species machinery that make one bacterium move twice over, once at continuous sub-pixel resolution and once at discrete grid resolution.

Bacterium

SURE

Acts as a wrapper for the state and physics of a single bacterium: initiating BacteriumPhysics, BacteriumSpecies, BacteriumState and GraphSearchPhysics. Takes in a target (row, column) pair in the maze during initialization and randomizes the subcell position.

Refers to SimulationSpeciesRegistry for bacterial movement engines and decides whether GraphSearchPhysics or BacteriumPhysics should be used. GraphSearchPhysics and BacteriumPhysics operate in distinct resolutions (discrete versus continuous) — most control algorithms can't operate on a non-pixelated structure (pixel-graph-based solvers in particular), while Markov-chain decisions need the higher resolution for behaviors to be tuned (discretized values lead to too few meaningful outcomes).

Applies move logic from either physics engine and addresses collision logic and directional weights of BacteriumPhysics, the class housing the stochastic bacterial model.

BacteriumPhysics

SURE

Sets directional weights and generates vector force directions. Bacterial orientation is derived from the current heading. Ray marching detects the distance from the bacteria to the wall: front, rear, left, and right (FRLR). These distances feed a force curve function (handled by ForceEngine), and the sum of the resulting attractive vectors (scaled by force, oriented by FRLR) becomes the attractive force vector — unit vector wallU[] — later scaled again by wWall. This process runs at discrete subpixel resolution due to computational cost. angleU[] is sampled from an angleNoise-distribution offset of the current angle; wMemory is applied to the current heading. These values are accessed fromBacteriumState, which stores the weights.

After applying these values to the movement vector, the resulting trajectory is calculated. This displacement and endpoint are verified by isReachable. If true, the position change is recorded. If the path contains a collision, a correction slides along the wall based on the interaction angle, randomly, if the collision is a perfect head-on. The path is traversed and the trajectory saved.

BacteriumSpecies

SURE

Resolves the engine choice if using a bacterial physics engine, and makes decisions regarding the appearance of the graphical entry by importing values from the species registry. Holds a name, an engine string ("weibull" or "mixed_gaussian", defaulting to Weibull), a double[] parameter set, and an AWT Color. resolveEngine() returns the matching ForceEngine.WeibullEngine or ForceEngine.GaussianMixtureEngine instance — the same class also backs the deterministic GraphSearchPhysics solvers, which are registered as species with empty parameter arrays and a fixed color rather than a force curve.

BacteriumState

SURE

The central processing hub for all bacterial statuses: bacterial trajectories (both pixel and subpixel resolution), angular heading, and the five tunable parameter inputs — stdDev, noise, wWall, wMemory, and wNoise. Also carries the logic for detecting exits and wall collisions.

ForceEngine

SURE

A stateless function called once per continuous step: it takes four local ray-cast distances and returns a force vector, with no concept of a visited set or the ability to backtrack. Handles both Weibull and mixed-Gaussian distributions, converting their parameters into a usable function and evaluating them at the current wall distances provided by ray marching (FRLR, as above). Weibull parameters are K, Lambda, Multiplier, and Baseline; mixed Gaussian are derived from Boltzmann force derivatives of position occupation and may take any number of 3-parameter Gaussian triples.

GraphSearchPhysics

SURE

Hosts movement logic for discrete grid-based maze solvers, alternatives to the continuous force-biased walk. Mutates the same package-private BacteriumState fields, one grid cell per tick, so a Bacterium running one of these looks and reports (trajectory/time/exited) just like a continuous-physics bacterium. These processes are deterministic: DFS/BFS-based algorithms need a persistent global state: a stack/queue of frontier cells and a visited grid that survives across many steps. Each model has a step function tied to its name:

DFS: stack-based walk; backtracks one cell at a time on dead ends.
BFS: queue-based frontier expansion; the rendered position jumps straight to whichever frontier cell is dequeued next, which isn't always adjacent to the previous cell (may appear to teleport when traced, a result of the tracing logic).
ORGANIC_BFS: same BFS frontier order, but the agent is a single physical walker that cannot teleport; reaching the next frontier cell means physically retracing steps back to the branching point, then walking down to the target. Total tick count reflects real distance travelled, directly comparable to the bacteria's tick-by-tick walk.
Shortest_Path: a BFS-based implementation that extracts the exact steps of the shortest walk to the exit.
Longest_Path / DFS_full: a DFS-based implementation that ignores the exit to explore the entire maze; once complete, makes its way to the exit. The longest path a deterministic process should take.
Naive_WALK: follows a randomly moving path; could technically live inside the bacterium physics engine, but is kept here to interoperate with the self-avoidant native walk, only implementable with memory structures.
Persistent_Naive_WALK: random walk with an added likelihood of repeating the same directional step.
Persistent_Naive_WALK_Wall_Follower: persistent random walk with an added likelihood of moving aligned toward a nearby wall (initially hypothesized as the minimum functionality of a bacterium; consistently the worst maze solver of all algorithms used in this project).
Self_Avoidant_Naive_WALK: random walk with an added weight against re-visiting an already-visited pixel.

SimulationSpeciesRegistry

SURE

A static lookup table of every built-in BacteriumSpecies the GUI can offer, plus the fixed Color[] palette (red / blue / green / orange / magenta / cyan) those species render in. Holds two parallel entries per wet-lab strain — a _weibull variant (K, Lambda, Multiplier, Baseline) and a _force variant (a mixed-Gaussian parameter set) — for EC, PP, VF, VN, and MM, plus one BacteriumSpecies per GraphSearchPhysics movement model (DFS, DFS_full_maze, BFS, organic_bfs, shortest_path, naive_walk, self_avoidant_naive_walk, persistent_naive_walk, persistent_naive_wall_follower), so the deterministic solvers appear in the same species picker as the stochastic force models. Main reads SPECIES_LIST to populate the species checkboxes and pre-fill their default parameters.

RandomNumberGenerator

SURE

The single Random instance behind every stochastic decision in the simulation  calling setSeed(long) makes an entire run reproducible. Exposes getSubPixelOffset() (uniform jitter in [-0.5, 0.5], used when a Bacterium randomizes its position inside its target subcell at construction), getRandomPosition(int) (uniform placement, legacy "RNG1"), and getDisplacementNoise(double) / getAngleNoise(double) both are rejection sampled Gaussians clipped to ±3σ of the supplied range, backing wNoise displacement and angular heading jitter in BacteriumPhysics/BacteriumState. getPositionNoise(double, int) is marked in its own comment as legacy and effectively unused.

02

Maze & Grid

The pixel grid itself, and every path that gets a wall/exit layout into or out of it, including bundled resources, custom CSVs, or hand-drawn images.

Maze

SURE

Owns the Pixel[][] grid, the list of Bacterium populating it, and a boundaryThickness (default 2) that BacteriumPhysics uses to limit legal bacterium positions near the edge. The constructor fills every cell with a fresh Pixel(r, c). Beyond simple wall/exit/count accessors, getPixelsOnLine(r1, c1, r2, c2) implements Bresenham's line algorithm to return every pixel a straight segment crosses — used for ray marching and trajectory rendering. clearWalls(), clearExits(), clearDensity(), and clearBacteria() each reset one dimension of state independently, which is what lets BatchThreading reuse a single Maze object across an entire CSV of runs without reconstructing the grid each time (unless the maze dimensions themselves change).

Pixel

SURE

The atomic cell of Maze.grid. Carries its own (row, col), a wall flag, an exit flag, and a visit count incremented once per bacterium pass via addCount() — that count is exactly what DensityMapPanel and OverlappedDensityMapPanel bucket into percentiles and colorize through InfernoColorMap, and what Maze.clearDensity() zeroes via resetCount() between batch runs.

FoldedPixel

SUREUNUSED

A two-field (count, isWall) value holder mirroring the subset of Pixel state a density renderer actually needs. Not instantiated anywhere in the current codebase — a stub left in place, presumably for a lighter-weight or serializable density snapshot that hasn't been wired up yet.

MazeFileLoader

SURE

The maze-parsing workhorse — loads a bundled int[][] maze either from the classpath (loadMazeFromResource, trying several lookup strategies to stay robust across IDE-run and packaged-jar execution, with and without a leading slash) or from an arbitrary filesystem path (loadMazeFromFile). Both funnel into parseMazeStream, which tries two parse modes in order: Mode A reads the file as literal Java-array source — stripping // comments and int[][] name = declarations, then reading brace-delimited {1,0,1,...} rows character-by-character; if no braces are found, Mode B falls back to a plain numeric matrix, stripping stray braces/semicolons and splitting each line on commas or whitespace. Either mode validates that every row has the same column count before returning, so a malformed maze file fails loudly rather than producing a ragged grid.

MazeImporter

SURE

Two static one-shot converters into the same int[][] (1 = wall, 0 = open) shape MazeFileLoader produces. importFromCSV(File) is a plain comma-split reader — no comment stripping or brace parsing, unlike MazeFileLoader. importFromImage(File) reads any ImageIO-supported raster and thresholds it to a wall/open grid by testing each pixel for exact opaque black (0xFF000000) — anything else, including anti-aliased edges or non-pure-black wall art, becomes open space. Used by OverlappedDensityMapPanelV2 when a maze is supplied as .csv or as an image rather than one of the bundled .txt resources.

MazeUtils

SURELEGACY

An earlier, narrower version of the array-style maze parser now living in MazeFileLoader.loadMazeFromFile — matches only {...}, / {...} bracketed rows line-by-line, with no plain-text fallback, no classpath-resource lookup, and no comment stripping. Not called from anywhere in the current codebase; superseded by MazeFileLoader.

MazeManager

SURE

A one-field holder (Maze maze) with a getter/setter, giving the rest of the simulation application a stable reference to swap the active Maze instance out from under UI components (MazePanel.setMaze, etc.) without those components needing to know a new Maze was constructed needed whenever a loaded maze's dimensions don't match the grid currently on screen.

MazeController

SURE.listeners

The Swing-facing counterpart to MazeManager owns the behavior behind the four "load a maze" buttons (Plaza, Uniform, Non-Uniform, Custom CSV) plus Save Maze CSV. loadPlazaMaze() clears walls and rebuilds just the outer boundary in place; loadUniformMaze() / loadNonUniformMaze() clear walls and delegate to MazeFileLoader.loadMazeFromResource() against the bundled mazes/ resources; loadCustomMaze() opens a JFileChooser, parses a binary CSV, and unlike the other three  replaces the Maze object entirely, since a custom file's dimensions rarely match the current grid. saveMaze() writes the current wall layout back out as a 1/0 CSV. Every load path ends in refresh(), which clears MazePanel's cached visuals and repaints. Note that MazeController is due for significant maintainance.

03

Graph & Skeleton Analysis

Collapses the per-pixel maze into a topological Region Adjacency Graph (specifically junctions and corridors treated as nodes and edges) for trajectory and shortest-path analysis.

SkeletonAnalyzer

SURE

Turns the raw wall/open Maze grid into a navigable topological graph, independent of and coarser than the per-pixel grid GraphSearchPhysics walks. analyze() runs a staged pipeline: (1) Zhang-Suen thinning reduces every open region to a 1 pixel wide skeleton; (2) each skeleton pixel gets a "degree" — not a raw 8-neighbor count, but the number of open→closed transitions walking clockwise around it, which lets an imperfectly-thinned junction still register the right branch count; (3) degree-0/1/3+ pixels are 8-connected-labeled into junction "blobs," while a wall-clearance BFS gives each blob a growth radius based on how wide the room or corridor around it is; (4) degree-2 pixels are labeled into edge components, with junctions acting as separators; (5) a weighted multi-source "Voronoi" BFS — junctions get a head start equal to their clearance radius, so wide rooms claim proportionally more territory — assigns every open pixel to its nearest junction (positive ID) or edge (negative ID) in regionMap; (6) buildRAG() scans adjacent regionMap cells to construct the Region Adjacency Graph.

Beyond the pipeline: deleteJunction(id) lets the maze editor merge a junction back into its neighboring edges; computeRegionTrajectory(Bacterium) discretizes a bacterium's continuous trajectory into a de-duplicated sequence of region IDs, with inferSkips() patching in a shared junction when a walk appears to jump directly between two edges; and shortestPath(src, dst) runs a plain BFS over the RAG treating junctions and edges as one bipartite node set. loadFromVoronoi(int[][]) can restore a previously computed regionMap without re-running thinning, at the cost of getSkeleton()/getDegree() returning null.

RAGGraphPanel

SURE

Read-only Swing visualization of a SkeletonAnalyzer's Region Adjacency Graph, laid out at the exact same cell size and dimensions as the maze it overlays. Paints wall cells dark, tints each open pixel with its region's HSB-derived color at low alpha (a soft Voronoi wash), draws each edge as a line between the centroids of its two endpoint junctions — or to its own centroid if it dangles — and labels edges "e{id}" and junctions "v{id}". getToolTipText() hit-tests the mouse against cached centroids to show a junction's connected edges or an edge's endpoints. Centroids come from SkeletonAnalyzer.computeRegionCentroids(), computed once and cached.

04

Visualization & UI

The interactive maze canvas, its density-map readouts, and the small Swing widgets that stitch them into the Bacteria List table.

InfernoColorMap

SURE

A grayscale-to-color LUT conversion matching FIJI's legacy "fire" color LUT, commonly used for visualizations of bacterial density. Used to create density maps in both the UI and for export.

DensityMapPanel

SURE

Renders Maze density as a heatmap, offscreen-renderable via toImage() (used by the batch export pipeline) as well as on-screen via paintComponent(). Colors are not scaled to the raw maximum count — render() sorts every pixel's count and colors relative to the 99th percentile, clamped to [0,1] and mapped through InfernoColorMap, so a handful of outlier hot cells can't wash out the rest of the map to a single flat color the way naive max-normalization would.

OverlappedDensityMapPanel

SURE

The live, in-app "Show Overlapped Density Map" view, wired from Main's button of the same name same percentile-normalized InfernoColorMap rendering as DensityMapPanel, plus a drawn black cell border per pixel. Distinct from overlap_processing.OverlappedDensityMapPanelV2, which is the offline/batch counterpart driven by overlap_simulations.csv rather than the live-in-memory Maze.

MazePanel

SURE

The largest UI surface in the app: Our interactive maze itself! Tracks six edit modes (SELECT, WALL, EXIT, ERASE_WALL, REMEDY_VORONOI, DELETE_JUNCTION) driven by mouse listeners, and  five independent overlay toggles (skeleton, Voronoi regions, bacterium trajectories, shortest-path overlays, degree debug coloring) that all read from an externally-supplied SkeletonAnalyzer set via setAnalyzer().

Hover state drives both a floating JWindow info popup (cell row/col/wall/count, or region/junction/edge info once an analyzer is attached) and tooltip text; mouse clicks in WALL/EXIT/ERASE_WALL modes mutate the underlying Maze directly, while SELECT mode supports Shift-click multi-selection for batch "Set Exit" operations. Also owns per-bacterium trajectory hover/click hit-testing used to pop up a bacterium's path on demand.

ButtonEditor / ButtonRenderer

SURE

A matched JTable cell editor/renderer pair that puts a live "Show Trajectory" button inside the Bacteria List table. ButtonRenderer just paints the button; ButtonEditor looks up the clicked row's Bacterium via Maze.getBacterium(row) and opens a JFrame dumping that bacterium's full trajectory as text. Eventually, all the buttons should be moved into a single spot (here)!

UserGuide

SURE

Not a class of logic; a String TEXT block used verbatim as the content of the in-app "?" help dialog. Walks through maze selection, maze interaction (hover / click / pin / Set Start / Set Exit / multi-exit), parameter and species selection, simulation controls, and the analysis tools (density map, overlapped density map, bacteria list). Note that it needs some work, especially with its legacy content!

05

Application Shell

Where everything above is instantiated and wired together into a single running program.

Main

SURE

The application entry point and, in effect, the entire Swing wiring layer: one very large main(String[] args) that constructs the JFrame, every button (maze loading, edit-mode, batch / overlap-batch, species checkboxes, direction-weight fields, create/start simulation, density / overlapped-density / bacteria-list windows, grid toggle, clear), and every action listener connecting those buttons to Maze, MazeManager, MazePanel, MazeController, Bacterium/BacteriumSpecies, BatchThreading, and the export_import package. Also owns a handful of small static parsing helpers (parseIntOrDefault, parseOrDefault for both double and double[]) used to read numeric parameter fields defensively. Nearly all classes in the project are instantiated somewhere inside Main. There are a few notable string arguments, which can be used for running simulations through a jar. or live application through another program or from the command line. This is extremely useful when doing some data mining, but is unimportant to most users :).

GUIPanel / MainMazeButtonPanel

SURESTUB

Empty class stubs package declaration and class body, no fields or methods. A bunch of unreferenced placeholders reserved for a future refactor that would pull Main's inline Swing construction out into dedicated panel classes.

06

Batch Processing

SURE.batch_processing runs every row of simulations.csv headlessly and exports each result to batch_output/run_<n>/. This is essential for all major simulations.

BatchSimulation

batch_processing

A plain data record for one row of a batch run: maze selection, species name, start (row, col), a semicolon/pipe-encoded exit list, timing (duration/dt/steps), movement parameters (velocity/stdDev/noise), direction weights (wMemory/wNoise/wWall), bacteria count, and the raw engine name plus pipe-delimited parameter array. It's quite short and sweet, being a constructor, but it is necessary to load items from simulations.csv.

BatchCSVLoader

batch_processing

Parses simulations.csv (header row skipped) into a List<BatchSimulation>, one row per line, comma-split into the 17 BatchSimulation fields with the parameters column further split on |. The maze-type column accepts "plaza", "uniform", "nonuniform", or "file:<path>" for a custom maze (classpath resource or filesystem path, resolved later by MazeFileLoader).

BatchThreading

batch_processing

Runs every BatchSimulation from simulations.csv on a background Thread so the GUI stays responsive. For each row: resets the live Maze (walls/bacteria/density/exits), loads the requested maze type — resizing the Maze itself to match the loaded grid if it's a custom file — applies the encoded exits, builds one BacteriumSpecies directly from the CSV's engine and parameter columns (color chosen by a small hardcoded EC/PP/VF/VN/MM → color switch), spawns bacteriaCount Bacterium instances with that species and the CSV's direction weights, steps every non-exited bacterium for duration/dt (or steps, if duration isn't set) ticks, then calls SimulationExportManager.exportRun(). waitUntilFinished() blocks the caller until the thread completes — used by the batch-overlap workflow, which needs batch trajectories on disk before it can visualize overlaps.

TrajectoryCsv

batch_processingSTUB

Empty class stub package declaration and class body only. Currently unreferenced.

SimulationExportManager

export_import

The current per-run export orchestrator, called once per batch simulation from BatchThreading. In sequence: DensityExporter (PNG), SummaryExporter (xlsx), FastCSVTrajectoryExporter (trajectory.csv — called twice in the current code, the second call redundant), MazeExporter (maze.json stub), then builds a fresh SkeletonAnalyzer for the maze and calls VisitMatrixExporter twice once across all bacteria, once successfulOnly=true. DuckDBExporter's Parquet export is wired in as a commented-out call and is not currently run. (Most users will never need chunk imaging, but we hope to eventually support it. The current implementation works, but is too slow for practical use.

DensityExporter

export_import

Renders a JComponent (typically a DensityMapPanel sized to the maze) to an offscreen BufferedImage via printAll() and writes it as density.png.

SummaryExporter

export_import

Writes summary.xlsx via Apache POI's streaming SXSSFWorkbook: one row per bacterium with its index, total elapsed time, and trajectory point count.

FastCSVTrajectoryExporter

export_import

The trajectory export actually used in the pipeline writes trajectory.csv as (bacterium_index, timestep, x, y) rows, buffering into a StringBuilder and flushing to a 16MB-buffered writer roughly every 1MB, to avoid excessive small writes across potentially very large trajectory sets.

TrajectoryExporter

export_importLEGACY

An earlier trajectory CSV writer — one row per timestep, one quoted "x,y" cell per bacterium column, padded with empty cells for bacteria whose trajectory ended early — plus a Parquet stub that's entirely commented out. Not called from anywhere in the current pipeline; superseded by FastCSVTrajectoryExporter's per-row-per-bacterium layout.

DuckDBExporter

export_importDISABLED

Writes every bacterium's trajectory to Parquet by spinning up an in-memory DuckDB connection, batch-inserting into a traj(bacterium_id, t, x, y) table, then running COPY traj TO '<path>' (FORMAT PARQUET). Currently disabled — its one call site in SimulationExportManager is commented out — in favor of the plain-CSV path.

MazeExporter

export_importSTUB

exportMazeJson() Currently, it only prints "add JSON here later" and writes nothing. We hope to support this in the future to allow maze simulations to be paused and restarted, but it is not a priority for now :,( .

VisitMatrixExporter

export_import

Writes a CSV: one row per bacterium, one column per junction vertex the analyzer's RAG produced counting how many times each bacterium's region-level trajectory (via SkeletonAnalyzer.computeRegionTrajectory, junction IDs only) visited each vertex. The successfulOnly flag restricts rows to bacteria that reached an exit; if none did under that filter, no file is written at all, so the "successful visit matrix" variant never emits an all-zero or empty CSV.

SimulationExportManagerOriginal

export_importLEGACY

An earlier version of SimulationExportManager same PNG / xlsx / CSV export sequence, without the SkeletonAnalyzer or visit-matrix step, importing XSSFWorkbook and ImageIO directly rather than delegating to the split-out exporter classes. Not called from anywhere in the current codebase (it's too slow), but we still hope to support it eventually, since Excel is much more user-friendly!

Overlap Processing

SURE.overlap_processing: the offline counterpart to the in-app overlapped density view, driven by overlap_simulations.csv against trajectory CSVs already on disk.

OverlapSimulationConfig

overlap_processing

A three-field record (maze file, pixel size, list of trajectory CSV files) describing one row of an overlap-comparison batch. Two near-identical classes share this name — the top-level SURE.overlap_processing.OverlapSimulationConfig and an inner static class of the same name nested inside OverlapCSVLoader; both hold the same three fields, and OverlapCSVLoader.loadCSV() constructs and returns its own nested variant rather than the top-level one.

OverlapCSVLoader

overlap_processing

Parses overlap_simulations.csv (mazeFile,pixelSize,csvFile1;csvFile2;...) and, for each row, constructs an OverlappedDensityMapPanelV2, forces it through a manual Swing layout/paint cycle (setSize + doLayout + printAll onto a BufferedImage — the panel is never actually added to a visible frame), and writes the composited result as a PNG into batch_overlap_output_folder/, named from the maze filename and every trajectory-CSV filename it overlaid. runBatchOverlap() is the entry point wired to Main's "Batch Overlap" button.

OverlapCSVLoaderOriginal

overlap_processingLEGACY

An earlier version of OverlapCSVLoader, same CSV format and PNG-export approach. Not called from anywhere in the current codebase; superseded by OverlapCSVLoader, which works with true CSVs instead of Excel Sheets.

OverlappedDensityMapPanelV2

overlap_processing

A DensityMapPanel subclass built entirely inside its constructor's buildMaze() static helper: loads a maze from a .txt (matched against the three bundled resource names), .csv (via MazeImporter.importFromCSV), or image file (via MazeImporter.importFromImage), builds a fresh Maze/MazeManager sized to it, paints in the walls, then re-reads every supplied trajectory CSV — expecting bacteria,timestep,row,column columns — rounding each (row, column) to the nearest pixel and calling addCount() on it. The resulting maze, with density baked into its Pixel counts, is handed to the parent DensityMapPanel's percentile-normalized InfernoColorMap renderer. This is the batch/offline counterpart to the live OverlappedDensityMapPanel.
